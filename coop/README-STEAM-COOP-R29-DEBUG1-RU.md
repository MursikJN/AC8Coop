# r29-debug1 — диагностика первого теста на двух ПК

Этот комплект добавляет журналы к экспериментальной r29. Нативные DLL взяты из
r29 без изменений: протокол 7, Steam-порт 391, задание 6 / «ПИЛОТ», F-14D гостя
вместо Бакстера. Новых игровых возможностей и результатов совместного полёта нет.
Игра при подготовке диагностического комплекта не запускалась.

## Подготовка и запуск

1. Оба скачивают и распаковывают **r29-debug1** отдельно от прежней r29. Не смешивайте
   файлы двух комплектов: лаунчер проверяет их контрольные суммы.
2. Хост запускает `Start-Host.cmd`, гость — `Start-Guest.cmd`. У обоих должны быть
   Steam-сборка игры 25201480 и разные аккаунты друзей Steam.
3. Оба нажимают обычный Enter на титульном экране и доходят до главного меню.
   Хост создаёт лобби через «Совместная игра» и отправляет приглашение Steam.
4. Для первого теста проверяем подключение, обе готовности, ожидание катсцен,
   ангар и вылет без боя. Перед вылетом подтверждаем готовность заново.

Маршрут и ограничения r29 сохраняются: произвольные миссии и оснащение гостя,
полная репликация оружия, урона и событий ещё не завершены. Первый совместный
полёт, реальная камера и локальные видео/звук гостя требуют проверки.

## Где лежат отчёты

После выхода или завершения процесса лаунчер автоматически создаёт ZIP в
`reports/`. Нужны **два архива: от хоста и от гостя из одной попытки**.
Не перезаписывайте их архивами из последующих запусков.

Если игра зависла или появилась проблема, можно сразу запустить
`Collect-DebugLogs.cmd` рядом с лаунчерами. Он сохраняет снимок последней сессии
в `reports/`, даже если игровая логика больше не отвечает. Выходить из игры или
ждать ещё одну ошибку для этого не требуется. Сам сборщик игру не закрывает.
Если процесс упал и лаунчер тоже был закрыт, та же кнопка собирает оставшиеся файлы.

Если запуск отклонён до создания игровой сессии, текст ошибки сохраняется в
`reports/launch-failure-*.json`. Приложите его вместо отсутствующего ZIP.

К двум архивам достаточно добавить короткое описание: что нажали, что увидели,
у кого возникла проблема и примерное время. Если штатная игра создала отдельный
дамп памяти, он автоматически в отчёт не включается; при необходимости его
можно будет разобрать отдельно.

## Что записывается

- Версия комплекта, контрольные суммы пакета и DLL, роль, идентификатор запуска,
  код выхода и результат удаления собственного загрузчика.
- ОС, версия драйвера и название GPU, разрешение и объём доступной системной RAM.
  Это не измерение свободной видеопамяти; её реальный расход пока не снимается.
- Изменения этапов, эпохи и поколения сессии; готовности, загрузки, подтверждения
  общих переходов и причины остановки.
- Каждая отправленная Lua-команда и полученное подтверждение с request ID,
  op, аргументами и числовой причиной отказа. Отмена отдельно показывает команду,
  которую она заменила. История каждого сетевого пакета не записывается.
- Получение приглашения, состояние Steam, RTT, готовность синхронизации часов,
  возраст локального состояния и интервалы между наблюдениями.
- Подготовка/запуск/завершение катсцены, идентификаторы локальных ассетов,
  остаток времени по плееру, оба голоса и ожидание второго участника.
- Состояние замены Бакстера и сюжетной привязки; native engine_detail,
  принятый ввод, число шагов модели, последовательности и режим наблюдения.
- На госте — этап загрузчика, проверка остановленного мира, число реплик,
  ожидаемые модели, возраст сцены, курсор событий, камера и причины её остановки.
- Периодические координаты хоста/гостя из уже собранного экспорта и поза реплики
  гостя. Это диагностические выборки, а не запись каждого кадра или видеозапись.
- Lua traceback при ошибке; свежие штатные журналы игры и текстовые данные
  аварии из текущего профиля и стандартного Saved, если сама игра их создала
  после начала этой попытки. Старые аварии из прежних запусков не подмешиваются.

Журнал не вызывает дополнительные игровые методы для осмотра объектов и не
вводит сетевые команды ради диагностики. Снимки снимаются примерно раз в секунду,
изменения состояния и команды — при наблюдении. Точность обнаружения промежуточных
состояний ограничена частотой публикации native status и работой игрового потока.

`mod/diagnostics-01.jsonl` … `04.jsonl` — журнал событий, а
`diagnostics-health-01.jsonl` … `04.jsonl` — отдельный журнал периодических
снимков. В каждом кольце четыре файла по 4 МиБ; телеметрия не вытесняет команды
из журнала событий. Для длительного теста старые записи внутри каждого кольца
вытесняются; число оборотов есть в `diagnostics-summary.json`.
Начальные сведения сохраняются отдельно в
`diagnostics-start.json`. Сборщик ограничивает размер архива и перечисляет
пропущенные файлы в `report-manifest.json`. Он исключает каталоги сохранений,
настроек и резервных копий. Отчёт содержит SteamID, игровые имена и пути,
которые встречаются в журналах; окружение целиком и ключи доступа не снимаются.

## Как сопоставляются два ПК

У каждого запуска собственный `session_id` и локальный `config_token`.
`epoch/revision/generation/scene`, SteamID хоста и команды помогают сопоставлять
состояния. UTC записывается для ориентирования, но часы Windows могут отличаться.
Метки `host_tick_ms` сравниваются только после `clock_ready=1`; это выборки
монотонных часов из native status, а не точное время каждого события.
Участие двух клиентов в одной попытке необходимо проверить по обоим отчётам.

В исходниках есть автономный анализатор:

```powershell
python scripts/analyze_coop_reports.py host.zip guest.zip --output build/coop-report
```

Он создаёт `analysis.md` и `analysis.json`: этапы, команды/отказы, последние
показатели и предупреждения о неполных отчётах. Сам по себе флаг «flight» не
считается доказательством рабочего кооператива. Анализатор не исполняет файлы
из архива и не извлекает их в игровую папку. Python нужен для анализа на стороне
разработчика; для запуска мода и сбора ZIP у друга он не требуется.

Общий перезапуск по-прежнему требует согласованного выхода и чистых процессов,
возвращает в лобби и нуждается в игровой проверке. Прогресс хоста сохраняется в
постоянном профиле мода, гостевой профиль создаётся заново на каждый запуск.
