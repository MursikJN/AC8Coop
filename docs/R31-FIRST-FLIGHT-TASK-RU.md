# ТЗ: довести R31 до комплекта первого совместного полётного теста

Дата: 22.10.2026. Статус: **подготовка локального комплекта выполнена без запуска
игры**. [Итог и ограничения](research/r31-kit-status-20261022.md). Игровая приёмка
остаётся невыполненной; публичный релиз не делался. Ниже сохранён объём задания.

## 1. Результат для пользователя

Подготовить одинаковый комплект для хоста и гостя, чтобы после распаковки они
могли пройти весь тест: Steam-приглашение → лобби → готовность → локальные
катсцены → ангар → повторная готовность → общий вылет → независимое управление
и камера гостя → остановка с автоматическим сохранением отчётов.

К утру нужен конкретный артефакт: ZIP, SHA256, два понятных запуска, инструкция
и проверенный комплект диагностических средств. Новые функции, не необходимые
для первого полёта, не должны откладывать выпуск этого кандидата.

Готовность комплекта к испытанию и успешный совместный полёт — отдельные
критерии. Без запуска игры можно подтвердить сборку, состав, протоколы и
автономные сценарии; фактический полёт принимается только игровым тестом.
Если обнаружится существенный незакрытый native-блокер, выдать точный отчёт
о нём; не объявлять кандидат рабочим ради формального выполнения срока.

## 2. Исходное состояние

Актуальные основания:

- [Общее ТЗ кампании](COOP-SPEC-RU.md) — целевая задумка.
- [R31: native owner](research/ac8-owner-native-r31-20261022.md) — текущие
  исходники, доказательства и ограничения.
- [Контракт подготовки и очистки](research/ac8-hangar-flight-contract-20261022.md).
- [MODLOG](../MODLOG.md) — история проверок и гипотез.

R29-debug2 — прежний диагностический комплект. Совместный полёт двух ПК на нём
не принят. R31 меняет расчёт движения: собственный F-14D гостя рассчитывается
на его ПК, хост получает и отображает результат. Backend R31 собран и прошёл
автономные проверки, но не выполнялся в игре. Лаунчер/упаковка R31 ещё не готовы,
loopback не конфигурирует новый backend. Это реальные незакрытые работы.

## 3. Фиксированный сценарий первого теста

| Параметр | Требование |
| --- | --- |
| Участники | Два ПК, два Steam-аккаунта, одна поддержанная сборка 25201480 |
| Миссия | Задание 6, внутреннее Mission007 |
| Сложность | «ПИЛОТ», штатное название; не вводить вымышленные названия |
| Хост | Выбирает свой поддержанный самолёт и двух остальных AI-ведомых |
| Гость | F-14D на месте Бакстера, стандартное вооружение, без модификаций |
| Отряд | Хост + гость + два AI; исходного AI Бакстера и пятого юнита нет |
| Имя | Steam persona гостя в штатной метке над его самолётом |
| Вход | Через лобби; Steam Invite основной, SteamID64 запасной |
| Прогресс | Сохраняется только хосту |
| Гибель гостя | Наблюдение до общего перезапуска |
| Перезапуск | Честно обозначенный fresh-process маршрут; не обещать повторный native spawn в том же процессе |

Это ограниченный первый полётный сценарий. Полная кампания, произвольные
миссии/самолёты/Parts, подключение посреди миссии, перенос хоста и принятие боя
не входят в эту поставку. Общее продуктовое ТЗ остаётся в силе для следующих
этапов. Неподдержанные варианты должны быть явно недоступны в интерфейсе.

## 4. Обязательные работы, по порядку

### 4.1. Единый профиль и проверка запуска

1. Привести сборку, Lua, DLL exports, протокол, переменные окружения и packaging
   к одной версии R31. Проверять совместимость до перехода в миссию.
2. Добавить отдельный лабораторный профиль и изолированный путь игры/сохранений.
   Лаунчер не должен молча использовать оригинальную установленную папку.
   В ZIP не включать игровые EXE, ресурсы, сохранения и декомпиляцию.
3. Подготовить `Start-Host.cmd` и `Start-Guest.cmd`, проверку обязательных файлов,
   хешей, сборки игры, корректных путей и отсутствия конфликтующей версии мода.
4. Предусмотреть режим проверки комплекта без запуска игры: параметры, путь
   DLL, exports, Lua-файлы и manifests проверяются без подключения к Steam.
5. Неподходящий профиль/версия должны давать понятную ошибку и отчёт.
   Не должно быть скрытого возврата к старому расчёту самолёта на хосте.

### 4.2. Замкнуть подготовку собственного самолёта

1. Провести аудит реального пути lobby → client world → resources/managers →
   Parts/Network → Finish → собственные модели → initial seed → камера → loaded.
2. Закрыть зависимости stock BeginPlay в generic world. Наличие manager/table
   должно подтверждаться проверками; нельзя заменять недостающий manager
   фиктивным указателем или подавлять ошибку готовности.
3. Подключить управляемый тестовый маршрут к **тому же native backend**, который
   используется настоящим гостем. Одной игры должно хватать для будущего
   отдельного теста модели; вторую игру на этом ПК не требовать из-за VRAM.
4. Стандартный профиль F-14D должен доходить до readback собственных моделей.
   Подготовка идемпотентна по командам; повторная команда не создаёт второй актор.
5. Сохранять Controller/default Pawn, собственные параметры модели и идентичности
   UObject; не копировать внутренности модели хоста. После ошибки останавливать
   подготовку и сохранять конкретный этап отказа.

### 4.3. Связать локальное управление, отображение и камеру

1. Ввод гостя немедленно вызывает штатную модель на его ПК; отправка результата
   и host echo не являются предпосылкой локального шага.
2. Хост применяет результат к существующему самолёту роли Бакстера. На этой роли
   не работают AI и второй независимый физический расчёт.
3. Гость видит собственный самолёт, местность и согласованные объекты сцены;
   камера следует собственному актуальному состоянию, а не запаздывающей копии
   хоста. Debug-карта не выдаётся за игровую клиентскую сцену.
4. Сохранить authority хоста для миссии/урона/смерти; owner_state не даёт гостю
   права задавать здоровье или сюжет. Не заявлять готовность оружия и попаданий
   без отдельной проверки.
5. Проверить порядок обработки sequence/timestamp, интерполяцию, stale packets,
   generation/revision, паузу и spectator. Время разных ПК не сравнивать напрямую.

### 4.4. Лобби и переходы без ручного дублирования меню

1. Steam Invite и запасной вход ведут в одну сессию с одинаковыми параметрами
   и именами. Гость сам не запускает одиночную кампанию.
2. Только хост выбирает миссию/сложность/ведомых и инициирует переходы.
   Изменение поддержанной конфигурации сбрасывает готовность обоих.
3. Сохранить два этапа готовности. Переходы требуют подтверждений текущего
   вылета от обоих; повторные/старые сообщения не запускают действие снова.
4. Катсцены у каждого воспроизводятся локально с изображением и звуком.
   Удержание Esc даёт голос 1/2; пропуск — только 2/2. Естественное окончание
   у одного участника не переводит второго дальше: ждём обоих. Голоса и loaded
   привязаны к текущему ролику, generation и revision.
5. Хост не отпускает вылет до реальной готовности модели/сцены/камеры гостя.
   Зависшая загрузка имеет срок ожидания и согласованный выход с причиной.
6. Кнопки отражают состояние операции, ошибки не оставляют интерфейс навсегда
   заблокированным. Искусственного ограничения полёта в 15 секунд нет.

### 4.5. Очистка, отмена и разрыв связи

1. Stop закрывает ввод/шаги/приём старых пакетов; возвращает камеру; снимает
   Lua-ссылки; проводит штатный Destroy/EndPlay и ожидает retirement объектов.
2. Destroy(true) не означает cleanup complete. Учитывать самолёт, Parts,
   Network, собственных детей и камеру. Отсутствующее выделение отличать от
   неизвестного результата выделения; неизвестное состояние — quarantine.
3. Проверить отмену до spawn, после spawn, после Finish, после loaded и во время
   полёта; разрыв на обоих участниках; поздний пакет после отмены; повтор stop.
4. До окончания cleanup запрещать повторное создание и restart ACK.
   Нельзя очищать чужие registry-записи или глобально сбрасывать менеджеры.
5. При необходимости нового процесса сообщать об этом явно. Сохранять отчёт
   до выхода и давать понятный маршрут повторного теста через лобби.

### 4.6. Автоматическая диагностика

1. Отчёты включены по умолчанию; отдельный CMD для обычного сбора не требуется.
   Сохранять итоговый ZIP при штатном выходе и доступные данные после сбоя.
2. Для сопоставления двух ПК фиксировать общий идентификатор попытки, роль,
   версии/хеши, generation/revision, этап, длительности и причины остановки.
   Не публиковать ключи, секреты и содержимое сохранений.
3. Писать жизненный цикл native actor/model/camera, identities, owner mode,
   readiness readback, число локальных шагов, отправленных/принятых/отклонённых
   пакетов, возраст состояния, паузы, таймауты и прогресс cleanup.
4. Логи ограничены по частоте/объёму; запись на диск не должна синхронно
   задерживать каждый физический шаг. Сохранять контекст до первой ошибки.
5. Добавить автоматический разбор пары отчётов: последний общий этап,
   расхождение версий/ролей, первичная ошибка, вторичные таймауты и незавершённые
   identity. Не объявлять отсутствие ошибки доказательством успешного полёта.

## 5. Реверс-инжиниринг — только по блокерам

Использовать `campaign-coop-research` и реально доступный GhidraMCP для точного
офлайн-бинарника. Приоритет: зависимости stock BeginPlay/flight model, владение
и update domains самолёта, destructor/EndPlay и необходимые ресурсы мира гостя.

Для каждого пробела: ID гипотезы → критерий → MCP-запрос/байты/caller → вывод
и статус в MODLOG. Проверять ABI по инструкциям и фактическому caller; не
выдумывать адреса, офсеты, сигнатуры, UObject layout или признаки готовности.
Обширный поиск всей репликации/кампании, не закрывающий блокер этого теста,
вынести в дальнейший план. Недоступность MCP записать и продолжить независимую
работу; не изображать подключение или runtime-доказательство.

## 6. Ограничения выполнения без участия пользователя

- Это задание само по себе **не отменяет прежний запрет на запуск игры**.
  Без отдельного разрешения выполнять код, сборки, автономные тесты,
  статический анализ и подготовку изолированного комплекта. Не запускать Steam
  для соединения и не ждать присутствия друга.
- Не менять оригинальные игровые файлы и настоящие сохранения. Не обходить
  DRM/античит/авторизацию, не подключаться к защищённым онлайн-сессиям.
- Не вводить новые подтверждения для обычных обратимых работ внутри этого
  объёма. При неизвестном ABI не экспериментировать native-вызовами наугад.
- Не публиковать релиз, не делать push/рассылку, не устанавливать комплект
  в оригинальную игру в рамках этого ТЗ. Подготовить локальный ZIP для проверки.
- Ночные сообщения и запланированные запуски не создаются автоматически этим
  документом. Выполнение начинается отдельным поручением пользователя.

## 8. Что пользователь проверит после подготовки

Составить отдельную короткую инструкцию под фактический архив R31, без
ссылок на ещё не опубликованный релиз и без требования редактировать код:

1. Распаковка, выбор изолированного пути, запуск хоста/гостя, вход в профиль.
2. Приглашение, одна сессия, имена и две готовности; одна проверка снятия
   готовности и повторного подтверждения.
3. Катсцена: 1/2, затем 2/2; отдельная попытка с более медленным участником.
4. Ангар: самолёт хоста, F-14D гостя вместо Бакстера, два оставшихся AI.
5. Вылет: обоим доступно управление после общего барьера; гость самостоятельно
   меняет крен/тангаж/газ, оба видят соответствующее движение. Камеры независимы,
   ник виден, пятого самолёта и AI Бакстера нет.
6. Предлагаемый первый прогон: не менее трёх минут без боя и искусственного
   15-секундного отключения. Фиксировать задержки и рывки, не объявлять их
   допустимыми без наблюдений. Отдельный прогон с задержками/разрывом связи.
7. Выход/отмена, подтверждение cleanup либо явного quarantine; повтор через
   предусмотренный новый процесс. Автоматические ZIP обоих участников.

Итог «совместный первый полёт подтверждён» возможен только после пункта 5–6
на двух ПК с обоими отчётами и фактическим независимым управлением гостя.
Успех лобби или макетное движение из имитатора этот критерий не выполняют.

## 9. Обязательная выдача по окончании выполнения

1. Путь к ZIP, версия, SHA256 и список проверенных/непроверенных функций.
2. Инструкция для двух участников и отдельный короткий порядок локального теста.
3. Сводка сборки/тестов с путями к журналам, не только числом тестов.
4. Перечень конкретных открытых блокеров, если они остались, и точный этап,
   до которого безопасно проводить испытание.
5. Обновлённый MODLOG и согласованный README; никакого заявления «полёт готов»
   без игрового результата. Не заканчивать работу на одной сборке DLL,
   если упаковка, предзапусковая проверка и инструкция ещё не завершены.
