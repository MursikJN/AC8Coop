# R30: перенос симуляции владельцу — состояние реализации

Исторический снимок R30. Продолжение с реализованным native backend и
актуальными ограничениями: [R31](ac8-owner-native-r31-20261022.md).

Дата: 22 октября 2026. **Частичная реализация; для совместного полёта не готова.**
Основание: [контракт подготовки и очистки](ac8-hangar-flight-contract-20261022.md).
Изменены только исходники/документация мода и локальные результаты сборки.
Игра, Steam-сессия и оригинальные игровые файлы этим этапом не запускались
и не изменялись. Новые native-адреса, офсеты и вызовы не добавлялись.

## Что реализовано в исходниках

- `native/guest_pilot_protocol.h`: экспериментальный AC8P v3, 392 байта.
  Новый `owner_state` содержит положение, quaternion, скалярную скорость и
  вектор скорости в координатах `Pose.position`. Только роль 1, F-14D (23),
  внутренний Mission007. Поля здоровья/смерти, вооружения, остальных самолётов
  и миссионных команд в таком сообщении запрещены. Пакеты управления стиком
  `input` не принимаются в конфигурации R30.
- `native/owner_flight.h`: контроллер локальных шагов и приёмник удалённой
  позы. После подтверждённой подготовки/общего барьера вызовы
  `Backend.step` и `Backend.camera` происходят до отправки, без ожидания ACK.
  Пропуск/ошибка отправки не откладывает уже разрешённый локальный шаг.
  Game backend обязан подтвердить объект и выполнить **игровую** физику;
  упрощённой физической замены в моде нет.
- Приёмник проверяет peer, оба nonce, generation, revision, последовательность
  и монотонный source timestamp. Source clocks разных ПК не сравниваются.
  Удалённая копия интерполируется с задержкой 75 мс; при молчании >300 мс
  новые позы не выдаются. Бесконечной экстраполяции нет. Потеря связи должна
  закрываться общим session policy; этот класс не заменяет его watchdog.
- `native/sortie_lifecycle.h`: отдельное ядро контракта с двумя peer/memberID/
  непрозрачными profile userid. Фиксируются миссия, сложность, самолёты,
  вооружение и модификации. Изменение revision сбрасывает обе готовности.
  Подготовка требует quiescence callbacks, снятия старых registry-ключей при
  сохранённых профилях, окончания старой очистки, согласованных представлений
  четырёх ролей и готовности обеих сцен/камер/начальных состояний.
  `Receipt` — результат readback будущего backend, не команда выполнить
  native-вызов. Сам по себе он ничего не создаёт и не освобождает в UE.
- Отмена меняет ticket и закрывает управление до очистки. Старые receipts
  больше не принимаются. Новый вылет нельзя начать до подтверждения освобождения
  камер, callbacks, registry, объектов и очередей; прежняя generation не
  используется повторно. Неоконченная локальная очистка запрещает новую
  подготовку. Нативный `memberID` не вычисляется из SteamID.
- Steam-путь различает направления host state / guest owner state, сохраняет
  проверки идентичности Steam peer и bounded queues. Для R30 отдельно выделены
  room protocol v8, invite v8, virtual port 392; совместимость с r29 не заявлена.
- Lua-парсер читает AC8P v3. Mesh renderer имеет вход для подтверждённой
  локальной позы гостя: host snapshot не откатывает её движение, а состояние
  здоровья/жизни берётся от хоста. Движение другого самолёта не меняется.
  Камера умеет брать эту локальную позу. Preview и неподтверждённый клиентский
  контекст такой вход включить не могут; смерть/despawn/teardown его сбрасывают.

## Что ещё не подключено к игре

1. **Создание и штатная инициализация локального F-14D в изолированном World
   гостя.** Старый r19/r29 путь требует существующий `LivePlayerPlane` хоста
   как источник конфигурации и начальных caches. В generic replica world
   такого источника нет. Перенос указателей/caches/vtables хоста через сеть
   недопустим и не реализован. Наличие mesh и загруженного класса F-14D не
   доказывает наличие рабочего flight model.
2. **Game-thread backend подготовки/очистки.** Для selector detachment,
   конфигурационной подписки, registry/actor release нужны проверенные
   вызовы и readback. Ядро Lifecycle проверяет условия, но сейчас ни
   `unsubscribe`, ни `detach`, ни `destroy` через него в игре не выполняются.
   Точные ABI/полный порядок этих операций предыдущая статика не закрыла.
3. **Связь этих backend с worker/клиентским циклом.** `LocalPilot` и `Receiver`
   проверены с тестовым backend, но production pilot их пока не запускает.
   Источник `guest-owner-local.ac8p` ещё не пишет игровая модель гостя;
   production context не устанавливает `local_owner_verified=true`.
   На хосте применение owner snapshot к реальному самолёту Бакстера также
   ещё предстоит подключить. Маршрутизация пакетов не равна движению actor.

Поэтому R30 `pilot_start` явно отказывает с причиной
`r30_blocked_guest_stock_bootstrap_and_native_sortie_backend_unverified`,
не переходя к старому host-input пути. Статус worker содержит
`owner_runtime_ready=0` и `native_sortie_backend_verified=0`.
**Это сборка исходников для разработки, не новый релиз/готовый игровой профиль.**
Лаунчер/архив R30 не выпускался. Существующий профиль r29 не переустанавливался.

## Проверки и ближайший тест

Сборка: `scripts/Build-SteamCoop.ps1 -Revision r30`, MSVC C++17 `/W4 /WX`.
Тестовый `TestModel` в `owner_flight_tests.cpp` проверяет порядок операций,
а не аэродинамику AceCombat8. Lua-тесты используют mock engine, без игры.
Точные результаты и хеши — в [MODLOG](../../MODLOG.md), локальные журналы —
`evidence/owner-simulation-r30-20261022/`.

Первый игровой тест назначается после реализации пунктов 1–3, а не по факту
успешной компиляции. Начать можно на одном ПК с одной игрой: отдельная гостевая
сцена + тестовый транспорт, проверка локального крена/газа и камеры без ответа
хоста, затем отмена/выход без утечки объектов. Это не требует второго окна.
Следующий этап на двух ПК: две взаимные копии, гость вместо Бакстера,
сохранение камеры хоста, четыре роли без AI-дубликата и поведение при задержках.
Оружие, попадания и полная сюжетная миссия принимаются отдельными тестами.
Ни один из этих игровых тестов сейчас не выполнен.
