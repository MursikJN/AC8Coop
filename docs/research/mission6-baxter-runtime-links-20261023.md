## B6-command: состояние, приказы и пределы проверки

Вращающийся наблюдатель перечитывал по одному AIState из трёх, сохраняя между
тиками только имена. Текущее native-состояние приказа не оказалось среди
прочитанных скалярных reflection-полей. Изменений этих скаляров не обнаружено;
это **не** доказательство отсутствия переходов AI.

Штатная команда ведомым в этом проходе не была отправлена: меню паузы показывает
настройки управления полётом, но не нужные назначения клавиш. Клавиши приказов
не угадывались. Поэтому критерий «команда → видимое подтверждение → изменение
состояния» остаётся непроверенным. Короткий полёт подтвердил работу штатной
сцены и реплики, но не этот причинный путь.

После выхода из миссии назначения найдены в **главном меню**:
«Система» → «Управление» → «Клавиатура и мышь» → «Назначение клавиш».
Снимок `wingman-keybindings.png`: стрелка вверх — «Приказ: лобовая атака»,
вниз — «Приказ: прикрытие», влево — «Приказ: рассред. атк», вправо —
«Приказ: вкл./откл. особое вооружение». Назначения не менялись.
Теперь поиск клавиш для следующего эксперимента закрыт; применение приказа
в полёте и native-переходы по-прежнему не проверены.

GhidraMCP повторно прочитал известные функции состояния/допуска. В дополнение
разобран повтор приказа в `0x147ed8760` (Ghidra VA, base `0x140000000`):
сравнивается byte manager+0xba; при том же значении вызывается обработчик
`0x147ef16f0` и увеличивается dword manager+0xc8. При другом значении byte
обновляется и обработчик вызывается с иной веткой аргументов. Создаётся событие
типа `0x74`. Полный сохранённый диапазон 633 байта сверён с офлайн EXE;
адреса/байты находятся в частном `order-instruction-validation.json`.
Названия native enum и назначение всех аргументов пока не установлены.

**Вывод для синхронизации:** новый одинаковый приказ игрока и повтор доставки
одного пакета должны различаться. Простая дедупликация по значению режима
может потерять штатный повтор. Это вывод из статического кода, не сетевой тест.

Прежние подтверждённые ограничения сохраняются: проверка состояния требует
AIWingmanPlane; допуск приказа ищет самолёт среди дочерних объектов WingmanUnits;
JoinOrLeave ищет его через WingmanPlaneList. Ссылки на предыдущие доказательства:
[движение и сеть](baxter-movement-network-20261023.md),
[команды и сценарные очереди](mission6-events-baxter-20261023.md).

## B6-preserve: что должен сохранить или заменить адаптер роли

1. Сюжетную идентичность Joker2, адресацию Unit, роль говорящего и связи HUD;
   пользовательский ник хранить отдельно от сюжетных идентификаторов.
2. Семантику присутствия/ухода/возврата роли, состояний команды и повторного
   приказа. Решение игрока лететь иначе не должно само включать AI-управление.
3. Контракты урона/уничтожения/условий пилота и временной неуязвимости;
   отдельно согласовать гибель игрока с продолжающимся сценарием.
4. Ссылки строя, backup-слотов, списков живых объектов, UnitMovement и менеджеров:
   все старые ссылки должны быть учтены при замене и очищены при travel/restart.
5. Идентичность сетевого Unit и отдельно самолёта/владельца. Текущий снимок
   не даёт оснований копировать runtime-адреса или GameObjectId между ПК.

Это перечень исследованных зависимостей, не доказательство достаточности
адаптера. Не выбрана неподтверждённая стратегия «подсунуть player вместо AI».
Сохранять нужно семантику контрактов, а не весь AI вместе с его управлением.
