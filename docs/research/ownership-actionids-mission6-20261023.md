## OAM1. Режим расчёта, сетевой ключ и родитель объекта различаются

### Назначение режима при создании AI

**Подтверждено статически.** В 0x147e09fe0 при создании AI-объекта:

- при отключённой сетевой ветке или spawnrecord+0x6a != 1 в object+0xed8 записывается 1;
- при разрешённой сетевой ветке читается результат 0x1474c70c0 и записывается результат + 2:
  соответственно 2 или 3;
- записи проверены в инструкциях 0x147e0a73b, 0x147e0a745 и 0x147e0a74d.

Ранее исследованные предикаты LiveAIWingmanPlane:
virtual+0xc38 выбирает локальный путь при +0xed8 != 2;
virtual+0xc40 при отсутствии делегирования проверяет +0xed8 == 3.
Это связывает назначение байта с ранее найденными локальным и удалённым путями расчёта.
Числа не переименованы в UE ENetRole: соответствие этому enum не доказано.

0x1474c70c0 дополнительно проверяет статус через 0x1474ca370, сетевой флаг +0x1fa
и совпадение двух внутренних ID через 0x1475039c0/0x147503ab0.
Прежний разбор связывает последние с локальным участником и первым возвращённым
участником комнаты. **Проверка аутентифицированного владельца самолёта/SteamID
этим не доказана.** Имя «host check» было бы преждевременным.

### Отдельная ветка ботов — не доказанный конструктор Бакстера

0x1471cb7e0 -> 0x147bb3df0 -> 0x147bb4480 передаёт режим через контекст+0x80;
последняя функция записывает его в самолёт+0xed8 и привязывает объект к Unit
через 0x147c951e0 / 0x147dca880.

Проверка класса в 0x147bb4480 использует getter 0x14728a2c0.
Свежая проверка имени 0x14cbf2b22 устанавливает **LiveAIBotPlane**.
Поэтому эту ветку нельзя автоматически называть созданием кампанийного Бакстера.

Позднее 0x1471cb7e0 перечисляет объекты списка менеджера через 0x147bb4aa0(..., 0xf).
При +0xed8 == 2 и ненулевом результате lookup 0x147bb77f0(object+0x4138)
он может сменить режим на 3 и обновить таблицу через 0x1474a8150.
Lookup ищет однобайтовый ключ в глобальной таблице и возвращает значение записи+8.
Семантика ключа, заполнение таблицы и связь с гостем кампании ещё не установлены.
Ни миграция хоста, ни передача владения по Steam здесь не объявляются доказанными.

### Сетевой ключ AI и порядок его подготовки

Конкретная vtable LiveAIWingmanPlane 0x14c5bbc00:

| Слот | Функция | Наблюдаемое действие |
|---|---|---|
| +0xc60 | 0x147cd6620 | Создать LiveNetworkAIPlane и сохранить в plane+0xed0, если его нет |
| +0xc58 | 0x147c96820 | Получить ID через plane+0xf50, virtual+0x20; установить net+0x28 |
| +0xc68 | 0x147cd6710 | Инициализация через 0x147c96880; при локальном режиме передать модель в 0x1474ad580 |

0x147c95830 вызывает эти слоты именно в порядке **создание -> ключ -> инициализация**,
после проверок GameMode, родительской цепочки и сетевого режима.

Ключ AI: uint32 ID, возвращённый интерфейсом, OR 0x0300000000000000.
Источник/стабильность самого uint32 ID ещё не восстановлены полностью.
Это не SteamID и не доказанный номер Joker2. Ранее найденная категория игрока 0x02
и категория AI 0x03 — разные пространства ключей.

Функция 0x147cd6710 имеет всего 69 байт; её хвостовой переход ведёт в 0x1474ad580.
Развёрнутый Ghidra хвост не принят за собственное тело этой функции.

### Что означает +0x518

0x147d20090(parent, child) записывает child+0x518=parent,
добавляет child в parent+0x508/count+0x510 и вызывает уведомление virtual+0xa28.
0x147d20270 удаляет child из списка, очищает +0x518 и вызывает virtual+0xa20.

**Вывод:** делегирование предикатов движения через +0x518 следует иерархии игровых
объектов. Это не указатель на сетевого пользователя и не самостоятельная проверка
права гостя управлять Бакстером.

## OAM2. Индекс действия — позиция в сохранённой таблице

### Регистрация компонента по ключу самолёта

LiveAIActionEventComponent: getter 0x146d05dd0, ctor thunk 0x146d08b60
-> 0x157935540; таблица действий находится в component+0xf0, менеджер в +0xf8.

0x147c59d60 получает AIActionEventManager, проверяет компонент и AI-владельца,
берёт ключ из owner+0xed0 -> net+0x28 и вставляет component в manager+0x78 по этому ключу.
Путь вызывается из weak-object callback 0x147ca3690.

**Ограниченная отрицательная находка:** в проверенном теле вставки нет отбрасывания
нулевого ключа. Если net отсутствует, локальное значение ключа остаётся 0.
Коллизия/неверная регистрация при раннем вызове — гипотеза о риске,
а не наблюдавшийся сбой. Полный порядок callback относительно создания net ещё открыт.
Соседний bind 0x147c59d10 -> 0x147c98f50 на owner+0xf58 сам по себе
не доказывает связь именно с callback 0x147ca3690: vtable у него другая.

### Преобразование класса в ID и обратно

Таблица имеет класс **LiveIndexSavedDataTable**: getter 0x146e88920,
ctor 0x146e984a0, vtable 0x14c795788. Метаданные подтверждают поле **KeyIndexData**
по +0xb0, количество элементов +0xb8. Элементы ключей занимают 8 байт.
Getter типа строки 0x146d06260 -> 0x1579161c0 подтверждает **LiveAIActionEventTable**.

Отправляющая сторона:

1. 0x147c5a180 создаёт/выбирает экземпляр действия по классу.
2. 0x147c99200 перебирает строки; predicate 0x147c9eb90 -> 0x147c5a420
   сравнивает класс строки с запрошенным классом.
3. Для найденного ключа ищется позиция в KeyIndexData.
4. Эта позиция записывается в action+0x3c. При отсутствии соответствия возвращается -1.

Приём: 0x147c99410 проверяет диапазон индекса, берёт KeyIndexData[index],
затем находит строку по этому ключу в row map. Virtual+0x2d8 таблицы —
короткий getter 0x1418bdfb0, возвращающий table+0x30.

Таким образом, это **индекс содержимого**, а не номер пакета, адрес класса или SteamID.
Предыдущий разбор отправителя уже установил передачу object ID и action index
в FLiveMessageAIActionEventExecute, без всей таблицы.

**Следствие, не готовая реализация:** участникам нужны одинаковые ключи объектов,
содержимое таблиц и порядок KeyIndexData. В исследованном пути отправки/приёма
проверка равенства таблиц не найдена. Это не доказательство её отсутствия во всей игре.
Загрузка/построение конкретной таблицы Mission007 и согласование при входе пока открыты.

### Связь сценария с компонентом действий

0x147c5a6c0 разрешает целевой объект через 0x14741e000,
находит LiveAIActionEventComponent через virtual+0x6f8,
вызывает интерфейс component+0xd8, virtual+8 с ключом действия.

Конкретный интерфейс: vtable 0x14c4aee78:
+8 -> 0x147c5a0f0 (lookup строки/класса),
+0x10 -> 0x147c59f00 (создание через 0x147c5a180 и помещение в менеджер).
Это подтверждает мост от сценарного исполнения к AI-действиям.
Конкретные вызывающие экземпляры задания 6 и имя класса исполнения здесь не установлены.

## OAM3. EventHash действительно ведёт в исполнение сценария

Предыдущий отчёт оставлял подписчика manager+0x1d0 неизвестным.
**Эта часть теперь установлена.**

LiveEventSubsystem: getter 0x1470b3d10,
ctor thunk 0x147483cc0 -> 0x15c38a910, vtable 0x14cb720a0.
Слот +0x318 -> 0x1474728e0.

Последовательность:

1. 0x1474728e0 подписывается на NetworkManager+0x1d0 через 0x147484130.
   Weak delegate сохраняет обработчик 0x147472960.
2. Ранее подтверждённый receive 0x1474e46c0 -> 0x1474ca100 сохраняет пару
   payload+0x20/+0x24, игнорирует повтор той же пары и уведомляет этот delegate.
3. 0x147472960 при результате 0 у 0x1474c70c0 вызывает
   0x147471190(subsystem+0x60, first, second).
4. 0x147470f90 находит контейнер по сравнению first с container+0x30.
5. 0x147471190 ищет в container+0xe0/count+0xe8 запись с entry+0x18 == second,
   разрешает контекст через 0x1474709b0 и передаёт одну запись в 0x14746ed90.
6. 0x14746ed90 исполняет условия через virtual+0x2e8,
   немедленное действие через virtual+0x2b8 либо задержанное через 0x1473ded40.
   Учитываются активность контейнера и локальные условия; получение сообщения
   не равнозначно безусловному исполнению всех эффектов.

Пару можно функционально описывать как **идентификатор контейнера + идентификатор записи**.
Алгоритмы вычисления этих значений, их устойчивость между загрузками и точные
имена полей сериализации ещё не восстановлены. Не подменяем их названиями «номер фазы»
или «порядковый номер сетевого события».

### Предпосылки и ограничения

В полном 707-байтном теле 0x147471190 сразу после возврата lookup 0x147470f90
читаются result+0xe0 и result+0xe8 — без проверки result на 0.
Lookup может вернуть 0. Инструкции 0x1474711bf..0x1474711d2 это подтверждают.

**Вывод из кода:** этот внутренний обработчик рассчитывает на уже существующий
контейнер. Произвольный вызов до его загрузки не является безопасным способом
синхронизации. Это не установленная причина прежнего падения гостя.

У отсутствующей/истёкшей записи также нет подтверждённого безопасного протокола
повторной доставки. В проверенном приёмнике пара отмечается до исполнения;
политику retry, сброс дедупликации при travel/restart и очередь до загрузки не восстановили.

Отправитель EventHash и условия, при которых именно он выбирает события для сети,
остаются открыты. Наличие получателя не доказывает полный реплей миссии.

### Что установлено именно для задания 6

Прежняя привязка пользовательского задания 6 к Mission007,
Joker2/Бакстеру и F-14D=23 сохраняется как историческое наблюдение.
В этом проходе не извлечены настроенные контейнеры/записи Mission007,
их фактические ID, таблица AI-действий Бакстера или полная последовательность целей.

Следовательно, нельзя утверждать, что события завершения движения 0x36,
команды ведомому либо все переходы Mission007 уже проходят по EventHash.
Подтверждён общий механизм доставки в сценарий; применимость к каждому событию
этой миссии ещё требует связи с её конкретными данными.
