# События кампании, Бакстер и граница синхронизации

23 октября 2026. Продолжение [разбора внутренних механизмов](mission6-internals-20261023.md).
Это результаты исследования, не ТЗ и не приёмка кооператива.

## Что изменилось в понимании

1. Команды сюжета обращаются к разным представлениям ведомого: Unit, дочерним
   AI-объектам, отдельному списку самолётов и менеджеру ведомых. Сохранение
   Unit Бакстера не сохраняет автоматически поведение остальных представлений.
2. Восстановлен путь очереди событий до вызова действий. Разветвление режима 2
   делит контейнеры между непосредственной и отложенной обработкой. Это не
   доказанные режимы сетевой отправки.
3. Команда `LiveCallRemoteEventExecution` создаёт именованное событие внутри
   этой системы. Слово Remote в имени не подтверждает отправку на другой ПК.
4. В сохранённых снимках Mission007 найдены соответствие Бакстера роли `Joker2`
   и реальные поля нужных объектов. Полного графа событий миссии в этих снимках нет.

## M6-E01: как команды доходят до ведомого

Классы связаны с функциями через class getter, конструктор, записанную им
таблицу виртуальных функций и слот исполнения `+0x2b8`. Это сильнее совпадения
имён. Семантика установлена только для перечисленных путей.

| Команда | Подтверждённый путь | Значение для замены Бакстера |
| --- | --- | --- |
| `LiveTakeDamageUnitHealth` | getter `146dec9c0` → ctor trampoline `146dfafc0` → `158d9bf40` → vtable `14c67f800`; execute `1473f5770` выбирает Unit из wrapper+28 по ключу интерфейса Unit+2a0 **или** группе Unit+1c8; `147dcb480` обходит Unit+2c0/count+2c8, вызывает damage virtual+0xa38 | По старой reflection это `ChildAIGameObjects`. Пустой массив не передаёт урон новому player. Дополнительно проверяются состояние режима и Unit |
| `LiveDestroyUnitExecution` | getter `146de9fe0` → ctor `146dfa010` → vtable `14c68b7a8` → execute `1473e22c0`; немедленная ветка `1473e2840` → `147dcb110` | Это сюжетное уничтожение через урон дочерним объектам, не готовый destructor самолёта. Есть отдельная ветка выбора объекта из wrapper+38 через интерфейс +f50; её тип нельзя автоматически считать player |
| `LiveUnitMoveLocation` | getter `146debad0` → ctor `146dfa990` → vtable `14c6847a0` → `1473edf70`; поиск `14741e4e0` по точному имени Unit; `147dd3ec0` назначает объект Unit+380 | Старый снимок называет поле `UnitMovement`. Смена этого поля не доказывает управление физикой нового player; дальнейшее исполнение движения требует разбора |
| `LiveWingmanJoinOrLeaveExecution` | getter `14706f8c0` → ctor trampoline `1470726e0` → `15bca9ef0` → vtable `14cb0bde8` → `147ebf7d0`; поиск `147ed8060` в manager+70 | Это `WingmanPlaneList`. Поиск проверяет weak identity и ключ интерфейса самолёта +f50. Сохранённый Unit в другом списке не заменяет эту запись |
| `LiveWingmanOrderExecution` | getter `147070100` → ctor trampoline `147072aa0` → `15bcbb950` → vtable `14cb0ca48` → `147ec18f0` → `147ed8270` / `147ed81f0` | Команда меняет состояние менеджера. Это не простой вызов по UnitName; есть проверки допуска команды |

Идентичность менеджера: trampoline `14782c760 → 15c45b180` использует class
getter `147075c80`, имя `LiveWingmanManager`. Часть кода getter-а преобразована
компилятором/защитой и содержит непрозрачные выражения; точный ABI не выведен.
Reflection старого сеанса независимо подтверждает `WingmanPlaneList=0x70` и
`WingmanUnits=0x80`.

`147ed8760`, вызываемый из обработки приказа, обходит `WingmanPlaneList`,
проверяет пригодность ведомых, обновляет состояние менеджера, вызывает
уведомления и создаёт событие типа `0x74`. Имена значений enum не угаданы.
Здесь не доказано, что новый player удовлетворяет проверки пригодности.

Сюжетный урон и уничтожение также проходят `1474c70c0`. Она отклоняет значение
типа миссии `0xc8`; при установленном флаге объекта из GameInstance+910
сравнивает результаты `1475039c0` и `147503ab0`. Ранее эти getter-ы были
прослежены до ID локальной модели комнаты и ID первого элемента списка
участников. **Первый элемент ещё не доказан хозяином комнаты.** Нельзя назвать
эту проверку готовым правилом authority для нашего мода или обходить её.
Это проверка допуска, не доказательство репликации результата урона.

Вывод: существующий адаптер одного пути script damage остаётся частным
решением. Нельзя помещать `LivePlayerPlane*` в AI-типизированные массивы ради
прохождения этих команд: совместимость остальных потребителей не установлена.

## M6-E02: очередь событий и что означает Remote

Установлена идентичность backend: **`LiveTriggerStackPlug`**.
`1470d2810` разрешает плагин по type ID через `147032160` / `147032de0`.
Имя подтверждено строкой по VA `14caa7f2e`; class getter `14702d0d0` ведёт к
конструктору `147032270`, который создаёт очереди и critical section.
`ALiveEventStack` содержит `OrcaBasicObjectPlugHolder`; это не доказанный NetDriver.

```text
Событие
  → маршрутизатор (пример: 147421660)
  → клонирование 147423bc0 → enqueue 147e04470
  → очередь TriggerStackPlug+50 / count+58

147471860: обработать уже подготовленные действия, затем подготовить новый буфер
  → 14746e240 → 14746e4a0 → условия и исполнение действий
  → обновить контекст через 147e04190
  → 147e042e0: очередь +50 → рабочий буфер +60 под блокировкой

Зарегистрированный callback 147e04030
  → подготовка контекста 147470130
  → worker 1474853f0 → 1474703c0
      → подбор контейнеров/действий через 147434500
      → записи результатов в context+58, count+60
  → эти записи позднее потребляет 14746e240
```

Регистрация callback найдена в интерфейсном методе `147e03d80`, который
сохраняет weak reference на объект и передаёт адрес `147e04030` в механизм
регистрации. Точный порядок потоков/зависимостей планировщика пока не доказан.
Диаграмма показывает зависимости данных, а не обещание исполнения за один кадр.

**Уточнение режима 2:** непосредственная ветка с параметром 1 обрабатывает
контейнеры, у которых поле `+d8` ненулевое. В queued worker при установленном
флаге записи обрабатываются контейнеры с нулевым `+d8`. То есть наблюдается
разделение обработки между двумя путями. Имя/назначение самого поля пока не
установлено. Это не основание назвать ветви «локальная» и «отправка гостю».

`LiveCallRemoteEventExecution`: getter `146ded2c0` → ctor `146dfb3c0` →
vtable `14c67cde0` → execute `1473f86b0`. При ненулевом поле имени `+58`
создаётся событие типа `0x4f`, имя копируется в payload, затем вызывается
`147421660` той же `LiveEventSubsystem`. Участок до выполнения очереди разобран;
соединение с serializer/STRIX/сетевым отправителем здесь **не установлено**.
Это не утверждение, что сетевых событий нигде в игре нет.

При сбросе интерфейсный thunk `147e04020` корректирует this на `-0x28` и
переходит в `147e03cf0`. Это ранее найденная очистка очередей/контекста.
Отложенные действия имеют отдельный механизм: `1473ded40` проверяет timer
handle и сохраняет weak identity. Полный контракт отмены всех таких действий
при смене миссии ещё не закрыт.

Вывод для дальнейшего исследования: одинаково воспроизводить имена событий
недостаточно. Имеют значение набор контейнеров, их флаги, счётчики, состояние
контекста и очередь. Ни готовая native-репликация, ни пригодность независимого
исполнения всего сценария на двух ПК этим исследованием не доказаны.

  `LiveAIWingmanPlane.AIWingmanStateComponent=0x4168`,

  по два элемента в списках менеджера, затем восстанавливал исходный граф.
  Он не доказывает, что итоговая замена совместима с командами менеджера.

  прямо записано `all_story_commands_bridged=0` и управление гостя ещё не разрешено.

В этих снимках присутствуют **описания классов** команд урона/уничтожения.
Это не экземпляры команд с параметрами, назначенные контейнерам Mission007.
Поэтому нельзя перечислить их как доказанно срабатывающие на Бакстере в миссии.
`Joker2` — установленная внутренняя роль данного снимка; её ключ нельзя без
проверки переносить на иной тип адресации или на все задания.

  очереди не является приёмкой очистки самолёта, камеры и удержаний после F9.

их связь с объектом сети Unit, опираясь на уже найденные поля и старые дампы.
