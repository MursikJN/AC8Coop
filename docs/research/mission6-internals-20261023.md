Восстановлен существенный участок общего исполнения кампании: выбор случайных
параметров перед стартом, передача этих параметров в состояние событий, допуск

идентифицированы подсистема повторов и последовательности окончания миссии.

Предварительное ТЗ не используется как доказательство внутреннего устройства.

## Артефакт, метод и ограничения

- Офлайн-копия `AceCombat8.exe`, 555102832 байта, SHA256
  `51510e2a520565dbe81fb0d569e95cd4393077acaaa859371489b80b8128829f`.
- GhidraMCP: Ghidra 12.1.4, x64 Windows, image base `0x140000000`.
  [Ответ о программе](../../evidence/mission6-internals-20261023/program.json).
  Build 25201480 и UE 5.4.3 — ранее установленная идентичность; текущий анализ
  подтверждает EXE по хешу, не определяет заново версию движка.
- Все адреса ниже — **Ghidra VA данного EXE**. RVA = VA − `0x140000000`.
  Смещения полей — наблюдения инструкций относительно конкретного объекта,
  не готовые C++ layouts. Смещения виртуальных слотов — байтовые.
- Декомпиляция сопоставлена с инструкциями из локального EXE через Capstone
  и границами PE unwind. Типы, имена параметров и ABI Ghidra не приняты на веру.
  В нескольких местах Ghidra включает код после хвостового перехода в тело
  вызывающей функции; это не дополнительный обычный call.
- Сырые ответы, в том числе ошибки распознавания функций, сохранены в
  [каталоге доказательств](../../evidence/mission6-internals-20261023/).
  [Manifest](../../evidence/mission6-internals-20261023/manifest.json) содержит
  SHA256 каждого файла. Время сохранения не выдаётся за время исполнения игры.
- UE4SS MCP среди доступных инструментов нет. Игра не запускалась; текущих
  runtime-наблюдений, проверок на двух ПК и готовых новых хуков нет.

## 1. Что происходит перед началом полёта

Проверенный участок, а не весь загрузочный автомат:

```text
CallStartMatch: 1478e6dd0
  → получить LiveRandomEventSubsystem: 147ededd0 / 146fc48e0
  → хвостовой переход в 147490170
      → по ID миссии найти категории 1..5 через 147364040
      → взвешенный выбор; сохранить пары выбранных значений

GamePlaying entry: 1478e7710
  → virtual b28 → 1478ee9b0 → 1471ce240
      → прочитать сохранённый выбор и таблицы
      → заполнить GameMode+3e8, count+3f0
      → virtual b50 → 1471c93e0 → 1471c9870
          → LiveEventSubsystem → найти контейнер → установить флаги
      → отправить событие типа 1 в маршрутизатор 1471eb4e0
```

Опорная таблица виртуальных функций кампании: VA `0x14cbc5b20`, ранее сохранена
в `evidence/campaign-coop-ghidra-20261022/responses/032-campaign_vtable.json`.
Фактические инструкции текущей проверки:
[mission-start-instructions.json](../../evidence/mission6-internals-20261023/mission-start-instructions.json),
[dispatch-instructions.json](../../evidence/mission6-internals-20261023/dispatch-instructions.json),
[identity-instructions.json](../../evidence/mission6-internals-20261023/identity-instructions.json).

`147490170` очищает массив подсистемы `+38`/count `+40`, обращается к пяти
категориям и использует `rand() & 0x7fff`, масштабирование и накопленные веса
12-байтовых строк. `147364040` ищет строки по ID миссии и категории. Затем
`1471ce240` сопоставляет выбранные значения таблицам. `1471c9870` находит
контейнер события по ключу через `147470ec0`; `14746cf60` устанавливает байт
`+e` найденной записи контейнера в 1.

**Вывод:** одинаковые номер миссии и сложность сами по себе не доказывают
одинаковый сценарий на двух машинах. Но какие из пяти категорий действительно
заполнены у Mission007 и что означают их значения, пока не установлено.
Передачу выбранных значений по сети этот участок не доказывает.

## 2. Найден настоящий маршрут обработки событий

`1470d2460` получает подсистему через class getter `1470b3d10`. Getter ссылается
на UTF-16 строку `LiveEventSubsystem` по VA `0x14cb6ec7a`; имя подтверждено
[чтением байтов](../../evidence/mission6-internals-20261023/event-subsystem-name.json).
Это основание идентификации, а не предположение по соседним сетевым функциям.

```text
событие → 1471eb4e0 (пример типа 1) / 1478f8730 (пример типа 38h)
  → проверка допуска 147472100
  → непосредственная обработка или постановка в очередь

непосредственная ветка:
  14746ddf0: обход контейнеров
    → 147434500 / 147434e50: выбор по типу события, группы 0..4
    → 14746e4a0: состояние узла, счётчики, ограничения повторов
    → 14746ed90: условия действий
        → virtual 2e8: проверка условия
        → virtual 2b8: действие без задержки
        → 1473ded40: отдельная ветка при ненулевом поле задержки

ветка очереди (разобранный пример):
  1478f9ff0 → 147e04470: добавить запись / запись с ключом
  дальнейший потребитель и выход в транспорт ещё не связаны
```

Инструкции подтверждают вызовы `14746ddf0 → 147434500 → 14746e4a0 →
14746ed90`, включая virtual `+2e8` по VA `14746f55b`, virtual `+2b8` по
VA `14746f8c2` и `1473ded40` по VA `14746f9c2`:
[event-executor-instructions.json](../../evidence/mission6-internals-20261023/event-executor-instructions.json).
Точная семантика задержки, поток исполнения и контракты конкретных наследников
действий пока не установлены; эти адреса не подготовлены для native-вызовов.

В `147472100` проверяются World, GameMode и пустота набора блокирующих причин
подсистемы (`+78`, число записей `+80`, число свободных `+ac`). Для одной ветви
кампании проверяется состояние transition helper (`GameMode+780`, helper+54),
virtual `+b70`, значения GameMode state `10/12` и `1471d2540`.
**Это не доказательство барьера готовности двух игроков.** Имена двух последних
проверок и остальные ветви допуска ещё требуют разбора.

`1474721c0` добавляет/удаляет байтовую причину блокировки и уведомляет реестр
при переходе между пустым и непустым набором. У контейнеров есть собственные
флаги, счётчики и ограничения повторного вызова. Поэтому повторная отправка
сырого события без знания этого состояния не доказана эквивалентной штатному
повторному запуску миссии.

Маршрутизатор имеет четыре ветви по параметру `0..3`: очередь, локальная
обработка и их сочетание с дополнительными флагами. Числа сохранены без
выдуманных имён enum. Ни очередь, ни наличие четырёх ветвей **не доказывают
сетевую репликацию**. `147e04470` в исследованном теле добавляет запись, а
вызова сетевого отправителя там не установлено.

## 3. Что нельзя смешивать с исполнением сценария

| Участок | Подтверждённая идентификация | Что из него не следует |
| --- | --- | --- |
| `1478528a0 → 146fe60d0`; операции `14784e260`, `1478486f0`, `147859550` | `LiveReplayWorldSubsystem`, запись/чтение структур повтора | Это не доказанный исполнитель событий миссии и не доказательство сети |
| `147083500` | `LiveWorldDataInterface`; обход реализующих интерфейс объектов | Имя интерфейса само по себе не означает менеджер сценария |
| `147ef1cd0 → 146ef1b10` | `LiveMiniGameManager` | Нельзя называть общим менеджером кампании |
| `1478ef050 → 146efb6f0 / 146efb7a0` | `LiveCampaignMissionEndSequence` / `LiveCampaignPlaneDeathMissionEndSequence` | Указатель GameMode+3d8 относится к завершению, не к основному исполнителю сценария |

Для первых трёх идентификаций сохранены `class-name-0/1/2.json` и
`subsystem-name.json`. Getter-ы классов окончания содержат имена в декомпиляции
и проверены инструкциями. Массив 16-битных значений, проходящий через
`147849ba0`, читается как завершаемое нулём имя: это не доказанный список ID событий.

`1478ef050` завершает прежний объект `GameMode+3d8`, выбирает один из двух
классов окончания с учётом состояния основного самолёта, создаёт новый объект
и вызывает virtual `+2b8` с параметром 3.0. `1471d0960` обновляет его;
`1471d08a0` вызывает завершение и очищает ссылку. Это **контракт объекта
последовательности окончания**, а не контракт удаления самолёта, камеры или
удержания класса F-14D.

Transition helper `1474916a0` содержит ожидание выгрузки/появления подуровней;
в одной ветви выполняется дальнейший сброс фазы через `1478e9b40`.
`147e03cf0` очищает очереди разобранного backend. Полный порядок сброса
объектов, callback-ов и регистраций игрока этим ещё не закрыт.

## 4. Что известно именно о Mission007

Соответствие задания 6 карте `/Game/Maps/Ingame/Mission007/PL_Mission007`
основано на прежних сохранённых наблюдениях, описанных в
[исходном аудите](mission6-baseline-20261023.md). Текущая работа не превращает
общие функции кампании в доказанный полный граф этой карты.

Проверены локальные копии 144-байтовых заголовков семи IoStore TOC. У основных
`pakchunk0/10/20-Windows.utoc` установлен признак Encrypted (flags 15), у трёх
optional-контейнеров flags 13, у global flags 4. Сырые заголовки и результаты
сохранены в [toc-headers.json](../../evidence/mission6-internals-20261023/toc-headers.json).
Разметка сверена с исходниками
[FIoStoreTocHeader](https://github.com/FabianFG/CUE4Parse/blob/master/CUE4Parse/UE4/IO/Objects/FIoStoreTocHeader.cs)
и [FIoStoreTocResource](https://github.com/FabianFG/CUE4Parse/blob/master/CUE4Parse/UE4/IO/Objects/FIoStoreTocResource.cs).

Содержимое сценария из этих контейнеров не извлечено. Чтение заголовков не
показывает, какие пакеты содержат все события Mission007. Списка целей,
подкреплений, обязательных диалогов, ветвлений, условий победы/поражения и
сценарных команд Бакстеру пока нет. Не подменять его строками EXE или
придуманным описанием миссии. Расшифровка или обход защиты не выполнялись.

Следующий обоснованный предмет исследования — связать конкретные классы
действий и условий из контейнера с обращениями к Unit/самолёту, затем установить
потребителя очереди и его реальную связь с транспортом. Одновременно нужны
имеющиеся разрешённые дампы/данные Mission007, чтобы отличить используемые
миссий действия от общего неиспользуемого кода. После этого можно оценивать
клиентскую сцену и составлять порядок реализации, а не закреплять его заранее.

Ни успешная декомпиляция, ни сохранённые инструкции не подтверждают игровой
полёт или исправление F9. Последний сеанс пользователь закрыл сам; его не
классифицируем как новый краш. Текущий комплект и код мода не изменялись.
