## M6M1. Движение сценарного Unit и самолёта — разные цепочки

**Подтверждено статически.** LiveUnitMovement: getter 0x1470552a0,
ctor 0x147061750, vtable 0x14caf1f00. Ранее найденная команда
LiveUnitMoveLocation через 0x147dd3ec0 сохраняет движение в Unit+0x380.

Unit constructor 0x147dc9da0 устанавливает vtable 0x14caf3040.
Слот +0x4f8 ведёт в 0x147dca240: при разрешающих условиях эта функция
обновляет AIPathTracker и вызывает 0x147dd31c0 для активного UnitMovement.
Движение использует цель, скорость, delta и условие завершения; изменяет
позицию/ориентацию Unit. Это не доказательство физического управления LivePlayerPlane.

Завершение 0x147dd3bf0:

- сбрасывает Unit+0x388 и Unit+0x380, деактивирует движение;
- проходит ChildAIGameObjects (Unit+0x2c0), проверяет LiveAIPlane и выставляет
  поле самолёта +0x29c8;
- при третьем аргументе 0 создаёт событие типа 0x36 с идентичностью Unit/цели
  и передаёт его в LiveEventSubsystem через 0x147df5120;
- замена движения через 0x147dd3ec0 использует аргумент 1, подавляя это событие.

Локальный маршрут продолжается через 0x147df84d0 -> 0x147e04470
(LiveTriggerStackPlug). Сетевой отправитель для данного события не установлен.

Дополнительная зависимость: 0x147dcc460 и 0x147dccb60 обновляют соответственно
InsidePlayers (+0x320) и InsideUnits (+0x330), формируют события 0x0c/0x0d.
Обработка проходит при Unit+0x3d9 != 0 **или** ненулевом количестве
AliveChildAIGameObjects (+0x2e8). Имя/смысл флага +0x3d9 пока не восстановлены.

**Вывод для дальнейшего исследования:** удаление AI из Unit может затронуть не только
самолёт, но и завершение движения/пространственные события. Визуально летящий игрок
сам по себе не доказывает сохранение этих сценарных условий.

### Физическое движение конкретного класса ведомого

Класс LiveAIWingmanPlane подтверждён getter 0x146d72a60 и constructor
0x147ed2100, вызывающим базовый AIPlane constructor 0x147cc9f50.
Его vtable 0x14c5bbc00:

| Слот | Цель | Наблюдение |
| --- | --- | --- |
| +0x4f8 | 0x147d1ba60 | Tick с ветвлением по режиму; в ветке 0 вызывает +0x8b8 |
| +0x8b8 | 0x147ed25d0 | Wingman override вызывает 0x147cce810 |
| +0xc38 | 0x147c96760 | Выбор ветки локального/полученного состояния |
| +0xc40 | 0x147c96790 | Условие подготовки исходящего состояния |
| +0xd68 | 0x147ccd3a0 | Вызов перед обновлением модели |
| +0xd70 | 0x147ccd3f0 | Вызов после обновления модели |

В одной из ветвей базового обновления:
0x147cce810 -> 0x147ccd260 -> 0x147cd2e90.

0x147cd2e90 при истинном +0xc38 обновляет модель самолёта (+0x2a70) через
0x144d30680; при истинном +0xc40 передаёт её сетевому объекту через
0x147bce640 -> 0x1474ad580. При ложном +0xc38 вызывает 0x147cd6760.

В 0x147cd6760 проверяется тип LiveNetworkAIPlane у объекта самолёта +0xed0,
читаются его поля состояния +0xc8/+0xd8; используются вторичная модель
самолёта +0x3630, расчёт движения и коррекция основной модели.
Последующее преобразование даёт позицию/ориентацию в полях +0x3550..+0x3578.

Полные короткие тела предикатов проверены отдельно:
0x147c96760 делегирует объекту +0x518, если тот есть; иначе возвращает
(plane+0xed8 != 2).
0x147c96790 делегирует при plane+0xdb9 != 0 и наличии +0x518;
иначе возвращает (plane+0xed8 == 3).
**Названия значений 2/3 и кто записывает этот режим не доказаны**:
нельзя подменить их догадкой «гость/хост».

Это подтверждает наличие ветвей локального расчёта и обработки сетевого
AI-состояния в классе ведомого. Не доказаны их активация в Mission007,
совместимость с LivePlayerPlane, полный формат движения и доставка через наш Steam-мод.
Blueprint-переопределения и фактическая периодичность остаются runtime-вопросами.

## M6M2. Какие проверки требуют AI

**Приём команд ведомого.** 0x147edaba0 (используется в маршруте WingmanOrder)
проходит WingmanUnits менеджера (+0x80), затем ChildAIGameObjects каждого Unit
(+0x2c0), сравнивает указатель дочернего самолёта с аргументом.
При совпадении возвращает Unit+0x388. Одного сохранённого Unit недостаточно.

**Состояние ведомого.** LiveAIWingmanStateStatement:
getter 0x14706d8d0 -> ctor 0x147072370 -> vtable 0x14cb108b0,
predicate +0x2e8 -> 0x147ebc060.
Предикат требует тип LiveAIWingmanPlane, получает AIWingmanStateComponent
из plane+0x4168, вызывает его virtual+0x508 и сравнивает с переводом
настройки statement+0x68 через 0x147ec46a0.
У конкретного компонента vtable 0x14c5b9ed0 слот +0x508 -> 0x146d73890:
это getter байта component+0x2e4, подтверждённый инструкциями.
Значения перечисления не переименовывались предположениями.

Wingman constructor сохраняет специализированный компонент +0x4168 из
унаследованного AIStateComponent +0x2808. Замена самолёта на LivePlayerPlane
не сохраняет автоматически эту проверку класса/состояния.

**Роль говорящего.** LiveHasWingmanSpeakerIDStatement:
getter 0x14706db90 -> ctor 0x147072430 -> vtable 0x14cb10f20.
Специализация +0x2f0 -> 0x147ebd6f0, короткий tail jump в 0x147ebd3e0.
Для нулевого значения настройки проверяется LiveAIWingmanPlane; для ненулевого
сравнивается строковая идентичность из объекта +0x448 с таблицей SpeakerID.
Это отдельная идентичность от желаемой надписи Steam-ника над самолётом.
Конкретный экземпляр этой проверки в графе Mission007 пока не найден.

**Дополнительный кандидат.** Полное тело 0x147cf0640 читает
state-owner+0xf0 -> AIPlane+0xfa0 -> Unit+0x388/+0x389 и в отдельных ветках
выбирает числовое состояние 0x0b. Точный виртуальный путь от компонента
Бакстера в эту функцию ещё не закрыт; не утверждается, что Бакстер вызывает её.

Прежняя привязка Mission007 -> Joker2/slot1 -> F-14D23 взята из исторического
снимка, описанного в предыдущем отчёте. Ни одна таблица классов не заменяет
граф конкретных настроенных условий/действий задания 6.

## M6M3. Реальные сетевые пути и их пределы

### LiveNetworkUnit: сообщение Health, не универсальный канал Unit

0x147dcf420 создаёт сетевой объект Unit+0x410. LiveNetworkUnit:
getter 0x146f0eb10, ctor 0x146f14040, vtable 0x14c889ee8.
Payload factory 0x1474cf7e0 -> vtable 0x14bfebfb8 -> type getter
0x1452c3dd0. Регистрация через 0x15456df10 содержит
FLiveMessageHealth / jp.co.soft_gear.strix.server.ext.message.game.FLiveMessageHealth,
поле Health по смещению payload+0x20.

Инициализация 0x1474e5690 регистрирует отправитель 0x1474e58a0 и
приёмник 0x1474e59b0. Переданный интервал 500 в 0x1474b5770 умножается
на 10000; единицы времени без проверки источника часов не назначены.
Отправитель копирует payload, обновляет время и вызывает
0x1474b59f0 -> 0x14a44c440 -> virtual+0x2c8 сетевого сервиса.

**Отрицательный результат с ограниченной областью:** полное тело приёмника
0x1474e59b0 (276 байт) проверяет тип сообщения и обращается к class getter
LiveUnit 0x146d0f1c0. В нём нет применения Health к Unit.
Это не доказательство отсутствия других каналов здоровья во всей игре.
Источник записи актуального Health также ещё не найден.
Нельзя использовать этот объект как уже готовую репликацию движения/событий Unit.

### FLiveMessageAIActionEventExecute: отправка и потребление подтверждены

Тип подтверждён регистрацией имени, type getter 0x1452c4230,
payload factory 0x1452c41b0 и vtable 0x14bfec058.

1. LiveAIActionEventManager (getter 0x146d05d20, ctor 0x1579352e0) доступен
   у GameMode+0x730 через 0x1471d4e60.
   0x147c58d50 выбирает допускаемое действие, формирует локальную запись
   из ключа сетевого объекта владельца и индекса действия.
2. При наличии GameMode+0x738 вызывает 0x1474ba1a0.
   Этот отправитель проверяет 0x1474c70c0, заполняет payload+0x20 младшей
   частью ключа объекта, payload+0x24 индексом действия, вызывает
   0x1474b59f0 -> 0x14a44c440 -> сетевой сервис.
   Проверку 0x1474c70c0 нельзя считать доказанной проверкой владельца комнаты:
   её пределы разобраны в предыдущем отчёте.
3. LiveNetworkGameMode initializer 0x1474b8f80 регистрирует приёмник
   0x1474baa70 для этого типа. Приёмник разрешает GameMode и добавляет
   запись размером 0x18 в очередь manager+0x58/count+0x60.
   Вторая 32-битная часть составного ключа устанавливается в 0x03000000;
   название этой константы не восстановлено.
4. 0x147c58d50 потребляет эту очередь: находит владельца по составному ключу
   в manager+0x78; сопоставляет существующее действие через 0x147c595e0
   либо разрешает индекс в таблице через 0x147c99410 и создаёт действие
   через 0x147c5a180. Далее используются virtual+0x2d0 (старт),
   +0x2c0 (обновление), +0x2d8 (завершение).
   В функции есть также локальные ветви постановки без сетевой отправки.

**Следствие:** обе стороны должны иметь согласованные ключи объектов и таблицы
индексов действий. Это вывод из наблюдаемого поиска, не готовый контракт подключения.
Проверка зависимостей 0x147c596f0 не доказывает дедупликацию сетевых пакетов.
Повторы, порядок, надёжность доставки, позднее подключение, travel/restart открыты.

Этот путь относится к AIActionEvent. Связь с общими событиями LiveEventSubsystem
(включая 0x36, 0x4f, 0x74) и всем сценарием Mission007 не установлена.

### FLiveMessageEventHash: отдельная обработка пары значений

Type getter 0x1452c5320, payload vtable 0x14bfec2b8.
0x1474e0c30 регистрирует приёмник 0x1474e46c0, который проверяет
LiveNetworkManager и передаёт payload+0x20/+0x24 в 0x1474ca100.
Там пара попадает в структуру manager+0x180; повторная пара не добавляется,
а для новой вызывается delegate+0x1d0 через 0x14469ca20.

Отправитель и конечные подписчики делегата пока не восстановлены.
Нельзя называть это ни полной репликацией миссии, ни только диагностикой.

## Что теперь установлено и что ещё открыто

Подтверждены три разных уровня: сценарное движение Unit, расчёт/сетевое
представление AI-самолёта и индексные сетевые команды AI-действий.
Механически заменить один указатель и считать все три уровня совместимыми нельзя:
обнаружены проверки класса, компонентного состояния, AI-списков и ключей действий.

Следующие исследовательские вопросы, **не изменение ТЗ**:

- кто присваивает plane+0xed8 и объект делегирования +0x518 при создании/переходах;
- кто заполняет manager+0x78 и таблицу AIActionEvent, как их ключи совпадают у peers;
- кто отправляет EventHash и кто потребляет его delegate+0x1d0;
- какие конкретные экземпляры условий/команд содержит Mission007 для Joker2;
