а не первый вход из ангара. Его точные режимы и именованные enum ещё не установлены.

## Новая статическая цепочка

`1478e3fe0` обновляет общий игровой автомат: читает байт GameMode `+578`,
вызывает разные virtual-обработчики состояний и обновляет helper из GameMode `+780`
через `1474916a0` (вызов по `1478e4016`). Числа состояний не названы по догадке.

У helper-а `+54` — отдельное состояние:

1. В состоянии 1 ждёт проверку `147edfb10`, записывает 2 и **хвостом** переходит
   в `1474919f0`. Это отдельная PE-функция, которую Ghidra включил в декомпиляцию
   вызывающей. Учитывать границы инструкций, а не размер псевдокода.
2. `1474919f0` вызывает `1478e9b40` для сброса/перехода состояния кампании,
   получает event subsystem и вызывает `14746d7e0(context)`, очищает очередь
   через `147e03cf0`, меняет disable-channel через `1474721c0(...,5,0)`.
   В конце формирует streaming requests через `1474937e0`.
3. В состоянии 2 проверяет, что прежние sublevels больше не имеют loaded-level
   pointer `+158` (получение через `14447ff60`). Затем пишет 3. При соответствующих
   режимах создаёт новый loader и задаёт ему список подуровней.
4. В состоянии 3 ждёт счётчик по `147930430()+1d0`, наличие loaded-level у новых
   подуровней и проверку `145c03750(1)`, когда target-loader валиден. После этого
   пишет 4. Это несколько разных условий; одного «экран загрузки исчез» мало.
5. Одна ветка завершает helper через `147492120`. Другая ставит callback:
   thunk `1474b2b70` (8 байт, `mov rcx,[rcx]; jmp 147492250`). Ghidra не распознал
   thunk как функцию; инструкции сохранены, точный ABI не выводится.

Класс создаваемых объектов `+60/+68` — **LiveStreamingLoader**:
`1474aff90` → getter `147015c50`, имя UTF-16 по `14ca6e49a` проверено чтением.
В `1474937e0` loader получает список имён и `+48=0`, затем `147ee10d0`;
в загрузочной ветке `1474916a0` другой loader получает `+48=1`.
Названия режимов следуют из проверок наличия/отсутствия sublevels; остальные
флаги loader-а и окончательная принадлежность переходу остаются открытыми.

`147492120` сбрасывает helper state `+54`, context `+58`, режимные поля `+40..50`,
индекс `+44=-1`, снимает ссылки `+60/+68` после native операций с UObject.
Это не доказательство немедленного GC и не контракт удаления самолётов/камер.

## Связь с катсценой и продолжением

`147492250` выбирает объект из записи этапа, проверяет режим и либо продолжает
через `1478ea200`, либо обращается к `14711e780` → getter `146ddd790`.
Имя этого класса — **LiveCinematicsWorldSubsystem**, проверено чтением
UTF-16 по `14c6503a2`.

В cinematic-ветке используется `147134280` и регистрируются два callback-а:
`147493590` в коллекции subsystem `+100` и `147493710` в `+130`.
Имена событий делегатов пока не восстановлены; не выдавать их за OnStarted/OnFinished
без дополнительной привязки reflection. `147493590` формирует локальное событие
через `1474b3720`; наличие этого вызова не доказывает отправку по сети.

`147493710` вызывает `1478ea200`, выполняет дополнительную операцию для основной
машины в соответствующем режиме и хвостом переходит в `147492120`.
`1478ea200` вызывает virtual `+a40` с числом `0x15`; имя этого перехода по одному
числу здесь не назначается. Следовательно, **загрузка и завершение cinematic-ветки
являются разными точками**, и сравнение длительности ролика не закрывает lifecycle.

## Контейнеры при повторе

`14746d7e0` обходит map контекста и вызывает `14746b9c0` для каждого контейнера.
В `14746b9c0` очищаются shared entries массива `+e0` (шаг 16 байт), освобождаются
связанные записи/обработчики и очищаются коллекции. Затем функция хвостом идёт
в отдельную `14746bdf0`.

`14746bdf0` читает источник контейнера `+440`, восстанавливает байт `+140` из
`+448`, обходит данные источника `+30/+38` и `+40/+48`, использует `14746ceb0`,
`14746cf60`, `14746c0e0`. Это подтверждает **очистку с восстановлением исходных
данных**, а не простое обнуление одного «миссия готова». Конкретные имена и
содержимое этих полей Mission007 не установлены — их нельзя подставлять в мод.

`1474721c0` добавляет/удаляет байт-ключ в наборе subsystem `+78`. Изменение между
пустым и непустым набором вызывает `14746dbf0`, который проходит контейнеры,
вызывает `14746c7b0` и записывает байт контейнера `+340`.
Ранее использовавшееся число 5 — ключ этого механизма; не номер миссии/пакета.

## Реализация наблюдения

- `probe/Mission6Capture/Scripts/capture.lua`: UDataTable rows, KeyIndexData,
  reflected maps/arrays/structs/references; исключение CDO, лимиты, явные gaps.
- `main.lua`: проверка игрового потока, coalescing запросов, опрос контекста,
  F8/F10, отказ от сбора при NetDriver. Никаких native offset reads/writes,
  ProcessEvent-вызовов, удержаний классов, GC или действий меню.
- `Prepare-Mission6Capture.ps1` и `Start-Mission6Capture.ps1`: отдельный runtime,
  хеши, plain paths, проверка существующей лаборатории, read-lock общих архивов,
  отдельный профиль и локальные логи. Оригинальный установочный каталог не цель записи.
- `summarize_mission6_capture.py`: сводка качества и найденных строк; отсутствие
  footer/ошибки не становятся «успешным полным снимком».

Подтверждение API: локальные `LuaUDataTable.cpp`, `LuaTMap.cpp`, `LuaUScriptStruct.cpp`,
`LuaTArray.cpp`, `Types.lua`. В используемой UE4SS.dll найдены имена UDataTable,
ForEachRow, GetRowStruct, TMap, IsInGameThread. Это не runtime-проверка их реализации
на конкретных объектах игры. UE4SS MCP в этой сессии недоступен.

## Что исследовать дальше — порядок

1. Получить первый заполненный снимок Mission007, проверить полноту и открыть
   недоступные важные поля отдельным read-only декодером, только если понадобится.
2. Связать container → package/event hash → condition/action → target/Baxter,
   сопоставить KeyIndexData со строками LiveAIActionEventTable.
3. Сравнить первый вылет и повтор: ID записей создания AI, состав Unit, action IDs,
   flags, случайные варианты и recreated objects. Разделить постоянные IDs и адреса.
4. Доказать точные completion callbacks для брифинга/вступления и ready-барьер мира.
   Отдельно пройти natural end, skip, restart, defeat/victory и возврат.
5. Закрыть отправитель EventHash, механизм дедупликации/сброса при повторе и набор
   событий, которые сеть действительно переносит. Получатель один этого не доказывает.
6. Проверить боевые зависимости роли: команды/AI actions, цели, оружие, попадания,
   урон/смерть и условия окончания. Затем писать ТЗ реализации по подтверждённой карте.

Новых инструментов сейчас не требуется. Главный недостающий материал — наблюдения
**заполненных данных** в штатном одиночном проходе. Для всего графа сценария одних
имён EXE, адресов функций и одного кадра в ангаре недостаточно.
