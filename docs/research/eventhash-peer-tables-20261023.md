## EPM1. Что удалось установить об EventHash

**Отправитель пока не найден.** Это результат ограниченного поиска, не доказательство
отсутствия отправителя во всём бинарнике или других модулях.

Уточнены имена полей:
virtual+0x18 vtable 0x14bfec2b8 ведёт в formatter 0x14525fa50.
Он связывает payload+0x20 со строкой **PackageHash** (0x14bfdb6f8),
payload+0x24 — с **EventHash** (0x14bfdb678).
Это подтверждает соответствие полей, но не алгоритм хеширования и не формат всего wire-пакета.

Проверены следующие кандидаты:

| Кандидат | Фактический результат |
|---|---|
| 0x1452c52a0 | Фабрика выделяет 0x28 байт и устанавливает vtable EventHash. В полном 116-байтном теле нет отправки |
| 0x1452a5010 | Найденные вызовы type getter 0x1452c5320 относятся к таблице type ID -> имя сообщения |
| 0x1474e0c30 | Регистрация приёмника EventHash, не найденная отправка |
| 0x1474e46c0 | Проверка типа и передача полей в 0x1474ca100, то есть приём |
| 0x1474e2080 -> 0x14525c130 | Отправляет другой объект с vtable 0x14bfec3d8; кандидат EventHash отклонён |
| 0x14746ddf0 -> 0x14746e4a0 | Исполнение локальных событий; в изученных телах не найдено построение/отправка EventHash |

Полный поиск RIP-relative LEA/MOV заданных форм в исполняемых секциях нашёл
одну ссылку на vtable EventHash: 0x1452c5301 внутри фабрики.
Прямых E8-вызовов фабрики сканер не нашёл.
Для type getter обнаружены четыре прямых вызова: два в регистрации имён,
один в регистрации приёмника, один в проверке входящего сообщения.
Косвенные вызовы, другие способы вычисления адресов и другие модули этим не исключены.

Важная поправка к методике: Ghidra DATA-xrefs 0x1613e9a68 и 0x1615ba528
находятся внутри PE exception directory. Это записи диапазонов функций,
**не вызывающие функции и не таблица отправки**. При проверке это установлено
по каталогу PE, а не предположено по отсутствию имени функции.

Приём и subscriber LiveEventSubsystem из предыдущего отчёта сохраняют силу.
Считать EventHash готовым полноценным каналом синхронизации миссии нельзя,
пока не найден источник и условия отправки.

## EPM2. Привязка самолёта игрока к участнику — прослежена до записей

**Подтверждено статикой, без проверки реального подключения.**

Цепочка:
slot -> LiveAircraftSelector.member ID -> удалённый PlayerPlane -> network key.

1. 0x1471cb3e0 перебирает настроенные слоты. Через 0x1474a5ae0
   получает member ID для слота и сравнивает с локальным member ID.
   Для другого участника вызывает 0x1471cd2d0 с **номером слота**, не с member ID.
2. 0x1471cd2d0 выбирает класс самолёта по данным настройки и передаёт слот
   в 0x1471cc490. В функции есть отдельная ветка GameMode+0x663;
   весь её смысл здесь не переименован в конкретный пользовательский режим.
3. 0x1471cc490 создаёт controller/plane, затем снова вызывает
   0x1474a5ae0(selector manager, slot).
4. Полученный 32-битный member ID записывается в plane+0x53b8.
   Если plane+0xed0 существует, net+0x28 получает
   uint32(memberID) OR 0x0200000000000000.
   В plane+0xed8 записывается 2 — ранее установленный удалённый режим.
5. По тому же слоту 0x1474c5080 находит строковый ключ профиля в roster map.
   Он используется для чтения выбора/оборудования; применяется 0x147d4ad20.
   Отображаемое имя и ключ профиля тоже копируются в поля самолёта.

0x1474a5ae0 в полном теле ищет selector+0x30 == slot и возвращает selector+0x2c;
при отсутствии возвращает -1.
Предыдущая цепочка заполнения selector по участникам комнаты подтверждена
повторным чтением 0x1474a35e0: member ID записывается в selector+0x2c,
отображаемое имя — в +0x48, сетевой ключ selector получает категорию 0x02.

**Следствие:** слот, member ID, строковый профиль и SteamID64 нельзя подменять
друг другом. Прямая связь member ID со SteamID64 данным участком не установлена.
Отдельной проверки -1 непосредственно перед записью в plane+0x53b8 в изученной
ветке нет; корректность заполненного roster — предпосылка вызывающего пути.
Это не доказательство приёма пакетов от любого пользователя: проверка отправителя
транспортом — отдельный вопрос.

### AI Бакстера использует другой источник ключа

Здесь закрыта прежняя неопределённость о getter из plane+0xf50.

- Конструктор LiveAIWingmanPlane 0x147ed2100 устанавливает
  secondary vtable 0x14c5bc978 по plane+0xf50.
- Её virtual+0x20 = 0x146d09560.
- Полный семибайтный getter читает uint32(interface+0x278),
  то есть **plane+0x11c8**.
- 0x147c96820 действительно передаёт this=plane+0xf50 и формирует
  uint32 этого поля OR 0x0300000000000000.
- Конкретная Wingman vtable+0xd20 = 0x147cd4b80 -> 0x147c91c10.
  Последняя копирует первые четыре байта записи создания в plane+0x11c8.
- 0x147e09fe0 передаёт запись создания в virtual+0xd20 до дальнейшего
  назначения режима и привязки к Unit.

Таким образом, ключ AI происходит от **ID записи создания**, а ключ удалённого
PlayerPlane — от **member ID участника**. Стабильность/выдача ID записи между ПК
и соответствие записи именно Бакстеру ещё не восстановлены.

Не называем plane+0x11c8 отражённым GameObjectId без доказательства:
историческая схема LiveGameObject указывает GameObjectId по другому смещению,
924 decimal (0x39c). Это разные наблюдаемые поля.

Ошибочный кандидат virtual+0xc98 проверен и отвергнут: он указывает на
0x146d09510, короткий setter byte+0x10d2, а не на инициализацию записи.
Правильный слот для найденной цепочки — +0xd20.

Это не готовая замена Бакстера гостем. Связь его Unit/сюжетной роли с PlayerPlane,
зависимости условий от AI и согласование двух пространств ID остаются открыты.

## EPM3. Конкретные таблицы Mission007: не найдены в доступном наборе

Проведён воспроизводимый поиск по сохранённым материалам:

- каталоги evidence, .tools/offline-research/targets и profiles/*/evidence;
- 3437 текстовых файлов: TSV, JSON/JSONL, TXT, LOG, с поддержкой UTF-16 BOM;
- junction/symlink не обходились; оригинальная установка и runtime-каталоги
  не сканировались; содержимое ZIP этим поиском не раскрывалось;
- запрос: LiveEventContainer, LiveEventPackage, LiveEventData, KeyIndexData,
  LiveAIActionEventTable;
- найдено четыре файла с именами типов/строками прежнего анализа;
  заполненные таблицы Mission007 по этим признакам не обнаружены;
- отдельных .uasset/.umap, AssetRegistry.bin и контейнеров .pak/.utoc/.ucas
  в этих каталогах нет; ранее сохранены лишь заголовки .utoc.header.

Список просмотренных файлов, их SHA256, совпадения и ограничения сохранены
в offline-artifact-inventory.json. Нулевой результат не доказывает,
что таблиц нет в игре или что они не могут иметь другое имя/представление.

Исторические TSV подтверждают объекты мира
/Game/Maps/Ingame/Mission007/PL_Mission007, но не дают содержимого event packages,
PackageHash/EventHash пар и KeyIndexData.
Прежняя проверка главных IoStore-заголовков показала Encrypted flag;
расшифровка/обход защиты не выполнялись. Данные миссии из EXE по одному имени карты
восстановленными не объявляются.

Для закрытия этого вопроса нужен содержательный разрешённый офлайн-экспорт
пакетов/таблиц Mission007 либо уже сохранённый снимок заполненных контейнеров.
Если такого артефакта нет, потребуется отдельно согласованное наблюдение
в изолированной игре. В этой задаче игра не запускалась и такой тест не выполнялся.
