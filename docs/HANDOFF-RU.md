## Исторический путь r6–r7

Начинаем с двух игроков. Каждый управляет своим штатным самолётом; на другой машине создаётся сетевая копия. Host в дальнейшем должен вести миссию и её результат. Ранние попытки вручную передавать оси самолёту ИИ оставлены как исследовательская история, а не основной путь.

Steam-транспорт 0.1.2 проверен отдельно в меню. R6 проверена с локальным состоянием; r7 соединяет транспорт с полётной копией, но требует первого совместного опыта в миссии. Исторические результаты r4–r6 ниже сохранены для разбора.

## Последняя проблема и следующий шаг

Сессия r4: 272 шага обновления, пять снимков без ошибок. Root и компоненты геометрии перемещаются, аргументы Move совпадают с фактической позицией. Основной компонент `plane+0x15A0`: raw `+0x188` у копии `0x41`, у исходного самолёта `0x61`. Отличается бит видимости `0x20`. Вторичный `plane+0x1AF8` имеет `0x43` у обоих и должен остаться без изменений.

В r5 реализован штатный setter RVA `0x42CE610(mainGeometry, true, 0)` после проверки создания и настройки моделей. Режим 0 не распространяет видимость на дочерние компоненты. Он обновляет состояние отображения штатным путём; простая запись байта не равнозначна этому вызову. Код политики находится в `native/plane_main_visibility.h`, адаптер и сохранение снимков — в `native/plane_flight_probe.cpp`. Проверены байты функции и её render-dirty пути в EXE точной сборки; [результат статической проверки](research/plane-flight-r5-static-validation.json). Живой запуск r5 выполнен: проверка остановила опыт до setter, из-за неверного индекса байта в окне +188..190. Все объекты удалены, выход 0, загрузчик снят. В r5.1 индекс исправлен по сохранённому raw-окну и добавлен регрессионный тест; следующий живой запуск r5.1 выполнен успешно по видимости. Пользователь увидел копию впереди, с тряской. Журнал: 215 шагов, все пять снимков без ошибок, основная геометрия 61, вторичная 43, координаты совпадают с заданными; F9 подтвердил retired. [Итог r5.1](research/plane-flight-r5_1-live-result.json). Выход игры ещё не проверен. Следующий узкий вопрос — плавность подачи позы (около 14,46 Гц, интервал до 422 мс); причину тряски пока не объявлять доказанной. См. [итог r5](research/plane-flight-r5-live-result.json). Исходный [контракт r4](research/models-r4-main-visibility-review.json) сохранён как историческое основание.

Не следует для этого включать целиком Actor/ИИ/оружие или все обновления компонентов. Перед следующим запуском подготовить исправление и нужную диагностику одним пакетом. Повторный запуск нужен под конкретную гипотезу/изменение, а не для ещё одной общей разведки.

## Жизненный цикл r4

F8 проверяет исходные объекты. F7 допускает одну проверенную попытку на процесс, после отдельного токена, привязанного к снимку. После создания собственных parts/network/plane заполняются кэши, выполняется Finish, проверяются компоненты, настраиваются модели и применяется поза. Подача движения ограничена 15 секундами. F9 прекращает её и запрашивает удаление.

Destroy=true означает принятие запроса, не освобождение памяти. Окончательный результат определяется по исчезновению всех собственных идентичностей. При непроверенном частичном создании используется quarantine и штатный выход из игры, а не повторное создание.

## Дальше, после видимого локального полёта

1. Передавать записываемое состояние через уже проверенный транспорт с ID участника и поколением миссии.
2. Создавать копию при согласованной готовности обоих участников, удалять при выходе/смене поколения.
3. Проверить движение двух игроков; затем оснащение, оружие, урон и авторитет Host над миссией.
4. Только после этого расширять до четырёх и добавлять пользовательское меню.

Выбор модели и оснащения должен происходить до миссии. В первом прототипе исследован F-14D; поддержку всех самолётов нельзя считать выполненной по наличию общей таблицы параметров.

R13 уже загрузил задание 6 после второго этапа готовности и отдельной кнопки хоста. В штатном составе подтверждены F/A-18C хоста и F-14D Бакстера. Это пока один игрок и три AI, а панель — имитатор.

### Steam backend компактного меню r24, 21 октября

По прямому запросу добавлена кнопка «Пригласить друга» через штатный ActivateGameOverlayInviteDialogConnectString. Оба игрока заранее запускают игру через лаунчер; запуск закрытой игры по приглашению не реализован. Private connect string ac8coop:v3:25201480:<host SteamID64>, не engine URL/console command. Payload лобби остаётся v3, ручной SteamID-вход сохранён. Для получения приглашений у обоих нужен r25.

native/steam_invites.inl включается AC8_STEAM_INVITES_R25 в steam_lobby_bridge.cpp, но имеет отдельный контекст на игровом потоке. После готовности уже созданного игрой Steam context регистрирует callback 337 (GameRichPresenceJoinRequested, 264 байта) и 331 (GameOverlayActivated, 8 байт). Не вызывает SteamAPI_Init/Shutdown/RunCallbacks и не перехватывает чужие callback. ABI проверен по официальному Valve Proton steamworks_sdk_157; нужные экспорты подтверждены чтением PE Steam DLL. DLL закреплена до регистрации указателей. Callback только копирует ограниченную очередь под SRW lock; проверки отправителя/формата/дружбы и публикация выполняются в tick мода. Никаких UObjects/переходов мира из Steam callback нет.

Lua слушает приглашения до создания комнаты. Подключение ждёт видимого MainTop, закрывает прежний worker при смене хоста, открывает гостевую страницу и использует существующий begin('guest'). Повтор того же хоста при рабочем соединении не сбрасывает ready; после DISCONNECTED позволяет переподключиться. Явный выход отменяет отложенное приглашение. Frontend получает room_role от контроллера; закрытие комнаты не открывает её повторно на следующем refresh. input_blocked не даёт кликам оверлея попасть в кнопки модового лобби и не воспроизводит их после закрытия Steam. Статусы/логи приглашения отдельные от ready ACK; открытие списка не называется отправкой или подключением.
